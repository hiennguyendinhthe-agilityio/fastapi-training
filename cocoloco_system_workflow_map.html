1. Bất đồng bộ Thuần túy (Asyncpg Pool)
  • Toàn bộ I/O path đạt 100% async/await, không nghẽn Event Loop.
  • Trình điều khiển PostgreSQL độc quyền asyncpg hiệu năng siêu cao.
  • Phiên làm việc độc lập get_db scoped theo từng HTTP request kèm tự động rollback.
2. Bảo mật RS256 JWKS & 2-Tier RBAC
  • Xác thực chữ ký số bất đối xứng RS256 qua Clerk JWKS bộ nhớ đệm LRU.
  • Độ trễ thời gian 5s clock skew leeway chống trôi lệch thời gian giữa các server.
  • Soft-Disable Active Guard & Admin Self-Lock Guard bảo vệ toàn vẹn tài khoản.
3. Toàn vẹn Đơn hàng (Atomic Tx & Snapshot)
  • Khóa giá cố định unit_price tại thời điểm checkout, không bị ảnh hưởng khi menu đổi giá.
  • Giao dịch Atomic Database bảo đảm hoặc tạo đơn toàn vẹn hoặc hoàn tác sạch sẽ.
  • Triệt tiêu vấn nạn N+1 query với cơ chế tải trước selectinload(Order.items).
4. Flutter Mobile & Session Persistence
  • Khôi phục tài khoản tự động bằng SharedPreferences trước khi render cây widget.
  • Cầu nối phản ứng AuthRoleNotifier giúp nút "+ Add Item" hiển thị tức thì khi đổi quyền.
  • Tương thích đa nền tảng iOS, Android và Web với mã nguồn kiểm thử 102/102 test sạch bóng.

📖 Defense Cheatsheet — Cẩm nang Bảo vệ Kiến trúc & Vấn đáp
Q1 Tại sao bắt buộc phải sử dụng asyncpg và SQLAlchemy 2.0 Async thay vì sync driver?
Trong FastAPI, nếu dùng driver đồng bộ (như psycopg2), mỗi query DB sẽ block Event Loop chính của tiến trình Python, làm toàn bộ các request khác bị xếp hàng chờ. Sử dụng asyncpg biến I/O mạng cơ sở dữ liệu thành Non-Blocking, giúp hệ thống chịu tải hàng chục ngàn kết nối đồng thời với mức tiêu tốn RAM cực thấp.
Q2 Cơ chế xác thực Clerk RS256 JWKS hoạt động như thế nào và tại sao cần bộ đệm LRU?
Clerk ký JWT bằng Private Key (RS256). Backend dùng PyJWKClient lấy Public Key từ Clerk JWKS endpoint để xác thực chữ ký. Bộ đệm LRU (Least Recently Used) lưu trữ Public Key tại local memory, loại bỏ hoàn toàn việc phải gọi ra ngoài Internet mỗi khi có request, giảm độ trễ từ ~200ms xuống dưới 1ms.
Q3 Tại sao trong order_items phải lưu unit_price snapshot thay vì query trực tiếp từ bảng products?
Giá sản phẩm trong catalog thay đổi theo thời gian (khuyến mãi, tăng giá cà phê). Nếu chỉ lưu product_id và query giá từ bảng sản phẩm, tổng tiền các đơn hàng trong quá khứ sẽ bị sai lệch khi giá đổi. Lưu unit_price snapshot bảo đảm tính bất biến tài chính (Financial Immutability) của hóa đơn.
Q4 Tại sao trong SQLAlchemy 2.0 Async phải dùng selectinload() cho Many-to-One và One-to-Many?
Trong async SQLAlchemy, cơ chế Lazy Loading ngầm định bị vô hiệu hóa hoàn toàn; cố truy cập quan hệ chưa nạp sẽ gây lỗi sập request MissingGreenlet. Dùng selectinload() sẽ phát 2 câu lệnh SQL tối ưu gom nhóm WHERE id IN (...), triệt tiêu triệt để vấn nạn N+1 query.
Q5 Làm thế nào để ứng dụng Flutter ghi nhớ tài khoản khi reload hoặc khởi động lại app?
Tích hợp thư viện shared_preferences vào SessionService. Khi người dùng đăng nhập, lưu role, token, và user (JSON) xuống ổ đĩa. Trong hàm main() của Flutter, gọi await SessionService.instance.init() trước khi gọi runApp() để đảm bảo phiên làm việc được phục hồi 100% trước khi dựng giao diện.
Q6 Tại sao nút "+ Add Item" trên màn hình chính Flutter cần Riverpod AuthRoleNotifier thay vì plain Provider?
Plain Provider<SessionService> chỉ so sánh tham chiếu đối tượng (identity equality). Vì SessionService.instance là Singleton, địa chỉ ô nhớ không đổi nên Riverpod bỏ qua việc rebuild. Sử dụng AuthRoleNotifier lắng nghe notifyListeners() và phát state mới AppRole, kích hoạt Riverpod rebuild lập tức hiển thị nút FloatingActionButton.
Q7 Hệ thống Cocoloco phân tầng và kiểm soát các mã lỗi RESTful như thế nào theo chuẩn RFC 9457?
Toàn bộ ngoại lệ được bẫy theo 5 tầng kiến trúc rõ rệt: Cửa ngõ Ingress (401 Bearer Token, 405 Method), Kiểm thực Schema DTO (422 Pydantic v2 Core Rust), Chính sách & Nghiệp vụ (400 Giỏ rỗng/Tự khóa Admin, 403 Phân quyền RBAC), Tầng Lưu trữ & Dữ liệu (404 Không tìm thấy món/đơn, 409 Trùng danh tính), và Hạ tầng Máy chủ (500 Che giấu lỗi an toàn, 502 Mất kết nối Clerk, 503 Quá tải DB pool, 504 Timeout). Tất cả đều trả về định dạng application/problem+json theo chuẩn IETF RFC 9457 có mã error_code bất biến, giúp ứng dụng Flutter (Dio Interceptor) bắt lỗi và hiển thị giao diện thân thiện mà không bao giờ bị crash.
Q8 Xử lý tải ảnh sản phẩm từ thiết bị (Local Upload) thế nào để vừa an toàn bảo mật vừa đồng bộ mượt mà với giao diện Flutter?
Trên ứng dụng Flutter, modal AdminProductFormModal sử dụng thư viện image_picker cho phép chủ quán chọn ảnh từ thư viện máy hoặc chụp trực tiếp. File ảnh được đóng gói dạng Multipart FormData và gửi lên endpoint POST /api/v1/uploads/image. Tại backend FastAPI, endpoint được bảo vệ bởi Guard require_role([UserRole.ADMIN]), kiểm thực nghiêm ngặt định dạng MIME (chỉ chấp nhận image/jpeg, png, webp) và giới hạn dung lượng tối đa 5MB. File được lưu trữ an toàn với tên UUID ngẫu nhiên tại thư mục static và trả về URL ảnh /static/images/... để Flutter gán ngay vào đối tượng sản phẩm mới.
T1 End-to-End Non-Blocking Architecture
Mọi I/O handler đều được khai báo async def, tuyệt đối không gọi time.sleep() hay requests đồng bộ làm nghẽn Event Loop.
T2 Soft-Disable Active Guard
Kiểm tra cờ is_active == True ngay trong dependency get_current_user, lập tức từ chối 403 nếu tài khoản bị vô hiệu hóa dù JWT còn hạn.
T3 Admin Self-Lock Guard
Kiểm tra trong PATCH /users/{id}/status: nếu current_user.id == target_user.id và is_active == False, trả về 400 Bad Request ngăn chặn Admin tự khóa mình.
T4 Atomic Order Checkout Transaction
Mọi thao tác kiểm tra tồn kho, nạp sản phẩm, trừ kho, tính tổng tiền và tạo chi tiết đơn hàng đều nằm trong một giao dịch cơ sở dữ liệu duy nhất (Atomic ACID).

Đoạn mã mẫu triển khai tại tầng Network của Flutter App, chuyển đổi Problem Details JSON thành domain exception an toàn: 
class ProblemDetailsInterceptor extends Interceptor {
  @override
  void onError(DioException err, ErrorInterceptorHandler handler) {
    if (err.response?.headers.value('content-type')?.contains('application/problem+json') == true ||
        err.response?.data is Map<String, dynamic>) {
      final json = err.response!.data as Map<String, dynamic>;
      final problem = ProblemDetails(
        type: json['type'] ?? '',
        title: json['title'] ?? 'Lỗi',
        status: json['status'] ?? err.response?.statusCode ?? 500,
        detail: json['detail'] ?? 'Đã có lỗi xảy ra',
        instance: json['instance'] ?? '',
        errorCode: json['error_code'] ?? 'UNKNOWN_ERROR',
        invalidParams: json['invalid_params'],
      );
      // Ném exception có cấu trúc thay vì crash app
      return handler.reject(
        DioException(
          requestOptions: err.requestOptions,
          response: err.response,
          error: problem,
          type: err.type,
        ),
      );
    }
    handler.next(err);
  }
}
